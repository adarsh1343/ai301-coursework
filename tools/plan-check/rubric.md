# Rubric: is this plan ready to post and build from?

A plan is ready when a maintainer could read it, see that it follows from the reproduced evidence and from what the thread already says, and let a stranger start building it without asking the author anything. Each check judges the thing itself (the cause, the change, the test), never the write-up's shape or length.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis matches repro | The plan's stated cause, read against the repro evidence block (the observed behavior, commands, outputs, file and line facts). | The plan states a specific cause, and that cause is the same one the repro evidence shows: it cites behavior, files, or lines the evidence actually contains and contradicts nothing in it. Fail if the plan names no cause, names a different cause than the evidence points at, or ignores a fact in the evidence that the cause must explain. | required |
| Fix targets the cause | The plan's approach and in-scope statement, read against the stated cause and the repro evidence. | Each change the plan makes removes the stated cause. Fail if the change only hides or works around the symptom (for example, patching the output while the cause the evidence points at stays in place). | required |
| Scope is bounded | The plan's in-scope statement, the files or areas it names, and its not-in-scope line. | The plan names each file or area it will change, and states as a topic what it will not touch. The listed changes add up to one bounded change that fits the issue. Fail if files are unnamed ("various files"), if there is no not-in-scope statement, or if the plan includes drive-by refactors or fixes unrelated to the issue. | required |
| Executable by a stranger | The plan's files, approach, and order of work. | Someone who has never seen the repo discussion could start now: the plan says which files to open, what to change in each, and in what order, and needs no answer from the author to begin. Fail if a step says only what to achieve ("improve the config handling") and not what to do. | required |
| Test plan is observable | The plan's test plan, read against the repro evidence's steps and artifacts. | The plan re-runs the repro steps (or a check built from their inputs) and states the specific output or behavior expected after the fix, so a before and after can be compared. Automated or manual both pass. Fail if it says only "test it" or "verify it works", or expects nothing observable. | required |
| Unknowns are stated honestly | The plan's risks and unknowns, and any claim in the plan or comment about code or behavior the repro evidence and repo-facts block do not show. | Anything the evidence does not establish is labeled as an unknown, assumption, or risk. Fail if the plan states an unverified claim as fact (for example, asserting other files are unaffected without having checked), or lists no risks while its approach has obvious ones. | required |
| Thread-aligned | The plan comment and the plan, read against the thread highlights and issue context (maintainer, collaborator, or repo-owner comments). | If a maintainer, collaborator, or owner has stated a direction, constraint, or objection, the plan accounts for it: it follows it, or says explicitly why it differs. Automatic pass if the thread has no maintainer, collaborator, or owner comments. Fail if such a comment exists and the plan or comment ignores or contradicts it. | required |
| Repo conventions followed | The plan comment, read against the repo-facts block (templates, contributing asks, contribution policy, AI-use disclosure rules). | The comment does everything the repo-facts block asks of a contributor posting a plan (required template fields, disclosure, claim-before-work rules, and so on). Automatic pass if the repo-facts block states no such asks. Fail if any stated ask is missing from the comment. | required |
| Comment stands alone | The plan comment on its own. | A reader who has not seen plan.md can find the cause, the change, and the test plan in the comment, with the key repro evidence quoted. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check fails. An `unclear` grade on a `required` check counts as a fail. `preferred` checks never change the verdict. The two "automatic pass" cases (no maintainer comments in the thread, no stated repo asks) are passes, not `unclear`. Quote the evidence for the deciding failed check in the output.
