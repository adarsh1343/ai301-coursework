# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the software version and platform the issue says it targets (issue context). | Pass if the record names the operating system AND an exact version (release number or commit hash) of the software under test, and those match the issue's target or the report says how they differ. Fail if the OS or version is missing, or the version is only a moving label such as "latest", "current master", or "main" with no commit. | required |
| steps-rerunnable | The repro report's steps, from starting state to the trigger, read as a stranger who has only the repo and this report. | Pass if the steps give the commands and inputs that trigger the behavior, so someone with the repo could run them and reach the trigger. Routine setup the repo's own docs cover (clone, install dependencies) does not need to be spelled out. Fail only if something specific to this bug is missing (a command, a file's contents, or a setting the trigger depends on) or if a step as written is visibly wrong (typo, wrong syntax, a file used but never created). Do not fail for minor gaps a competent reader would fill from the repo docs. Judge whether it can be re-run, not how many steps there are. | required |
| behavior-matches-issue | The artifacts in the repro report (output excerpt, log, screenshot) read against the symptom the issue describes (issue context). | Judge whether the artifact comes from the issue's own scenario, whichever outcome the report claims. If the report says "reproduced", pass if the artifact shows the same underlying symptom the issue describes (same kind of error, same wrong result); wording, formatting, line numbers, and platform details may differ. If the report says "cannot reproduce", pass if the steps and artifact are a good-faith attempt at the scenario the issue describes (the same command, layout, or configuration, as far as the attempt's environment allows) and record what was observed instead. The attempt does not have to match every condition of the issue: a different OS, shell, or input is fine, and output that runs fine is expected, as long as the report states the difference. Fail if the artifact comes from a different scenario than the issue's, shows a different failure or adjacent problem, or is a setup or syntax failure. Unclear only if the excerpt is truncated so the scenario or result cannot be told at all. | required |
| outcome-honest | The report's stated conclusion (reproduced or cannot reproduce) read against its own artifacts and environment record. | Pass if the conclusion is exactly what the artifacts support. "Reproduced" needs an artifact that shows the issue's behavior. An evidenced "cannot reproduce" also passes: it shows the environment, what was run, and what was observed instead. Fail if it says "reproduced" while the artifact shows something else, states a cause or fix the artifacts do not show, or says "cannot reproduce" with nothing shown. | required |
| conventions-followed | The repo-facts block (templates, contribution policy, AI-use rules), read against both the claim comment and the repro report. | Pass if the comments follow the templates and required sections the repo-facts block names AND, where the repo-facts block says AI assistance must be disclosed, the comments contain a disclosure. Pass if the block sets no such rule. Fail if a stated requirement is not met, including a required AI disclosure that is absent. | required |
| claim-specific | The claim comment, read against the issue's description. | Pass if the claim names something particular to this issue (its symptom or component) and states what the author will do next (investigate and report back), with no promised fix and no date. Fail if it could be pasted onto any issue, or promises a fix or a time. | required |
| expected-vs-actual | The repro report, read for a stated expected result next to the observed one. | Pass if the report says what should have happened and what happened instead. | preferred |

## Verdict rule

Accept if every required check passes. Preferred checks never change the verdict. An unclear grade on a required check counts as a fail, so the package is rejected.
